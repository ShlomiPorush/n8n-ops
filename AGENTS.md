# AGENTS.md

## Project

n8n-ops is a self-hosted operations console for many n8n instances: failure monitoring and problem grouping, Telegram alerts and email reports, MCP and REST access for agents, encrypted backups to one or more destinations (S3-compatible, a mapped folder, SFTP, WebDAV), and instance consolidation.

**Stage: v1 released as 0.1.0 (2026-10-22).**

- Product requirements: `docs/requirements.md`
- Foundation and repository contract (what exists, decisions, scripts, CI): `docs/project-foundation.md`
- Domain language (use these words in code, UI and docs): `docs/CONTEXT.md`. It includes accepted decisions that are not built yet (see `docs/adr/`); check the code for current behaviour.

Items marked planned in those documents do not exist yet. Check the repository before assuming a file, command or feature.

## Repository policies

- The repository is public. Everything tracked is in English. `scripts/verify.sh` fails on Hebrew characters.
- Never commit environment-specific details: instance names, hostnames, IP addresses, local paths, API keys, tokens or passwords. They belong in the ignored `docs/private/` or in ignored environment files.
- **Secrets.** Keep secrets out of the repository and its documentation. An environment file a stack loads is tracked only as an example (`.env.example`, `docker/env/*.env.example`) with variable names and empty values or obvious placeholders. No tracked file of any kind holds a working value for a secret-like setting: a password, key, token, signing or encryption secret, or a connection string with credentials. Development, test and CI stacks get no exception, and neither does a value labelled fake, dev-only, test or not a secret, bound only to loopback, or said to guard nothing real. Every secret a stack needs comes from a cryptographically secure random generator: the development stack makes its own once, on the developer's machine, in its owner-only env directory and never overwrites them; `scripts/verify.sh` and CI make new ones for each run; tests make the passwords and keys they use with `randomBytes` or read them from the run (`E2E_ADMIN_PASSWORD`, `E2E_N8N_OWNER_PASSWORD`). Credentials for external services come from the CI or local secret store. A stack refuses to start when a required secret is missing or is a placeholder (`check_stack_env` in `scripts/lib/common.sh`, `loadConfig` in the server, the production `postgres` entrypoint). A secret value that was ever committed is public: never reuse it, and tell the owner where it must be replaced. An existing file that breaks this is not a precedent: report it instead of copying it. In work that touches secret-like settings, put these rules in every brief and reviewer prompt, and treat a violation as a blocker. The guards fail on a tracked env file that is not an example.
- The product UI is English only and LTR only. Do not add localization or RTL support.
- Keep the repository root minimal. Every root file is listed and justified in the foundation document.
- Add user-visible or operational changes under `Unreleased` in `CHANGELOG.md`, written for the next release (no Changed or Fixed entries about things that were never released). Do not bump versions in pull requests; the Release workflow does that.
- Install with the lockfile (`pnpm install --frozen-lockfile`, done by the scripts).

## Layout

- `apps/server`: Hono on Node.js, Drizzle with PostgreSQL (migrations in `apps/server/drizzle`, generated with `drizzle-kit generate`, run on start). `src/routes` are HTTP routers, `src/services` hold the logic (problems, alerts, health, backups, workers, workflows, moves, agent queries), `src/features.ts` mounts routers and scheduled jobs. Tests named `*.integration.test.ts` need the verification stack (a real PostgreSQL, S3Mock, OpenSSH and rclone WebDAV) and run only from `scripts/verify.sh`. Serves the built UI. Never mounts the Docker socket.
- `apps/web`: React, Vite, Tailwind CSS, shadcn/ui primitives, React Router, TanStack Query. One app, one set of pages and functions, drawn in two designs (below). Every colour, size, radius and shadow is a token in `src/index.css`; `src/design.test.ts` guards them. Pages use `src/components/kit.tsx` and the shared behaviours (`save-bar.tsx`, `confirm.tsx`, `filter-bar.tsx`, `ui/table.tsx`, `ui/dialog.tsx`, `lib/toast.ts`, timings in `lib/behavior.ts`); follow the v3 behaviour rules they implement. End-to-end specs in `apps/web/e2e` run in file order against the test stack and share state through `test-results/e2e-state.json`.
- **Backups go through destinations** (`apps/server/src/services/destinations/`). A run has one copy per destination (`backup_copies`), fixed when it starts. The archive is age-encrypted where it is made; the worker uploads it to the server (`/api/worker/jobs/:id/archive`, with a signed single-use token that `upload-url` returns, so workers of earlier releases work unchanged), the server keeps it in `/data/spool` and `backup-copies.ts` writes and verifies each copy (size and SHA-256), retries, applies the destination's retention and settles the run (ok, partial, failed). Every store implements the contract in `destinations/store.ts`; `stores.integration.test.ts` runs that contract against a real server of each kind. A destination's Location (`location`) never changes once set, and two destinations may not overlap, so retention never removes another one's archives.
- **Agents connect by approval** (`apps/server/src/oauth/`). `oidc-provider` (pinned) is the authorization server, mounted in Hono for `/oauth/*`, `/.well-known/oauth-authorization-server` and `/connect/device`, issued under the public URL; its records live in `oauth_store` (`store.ts`). Every approval is a grant of its own and an `api_tokens` row of kind `agent` (`grant_id`), so access requests, the audit log and revocation treat it like a token. `requireToken` takes a token made by hand or an opaque access token for that resource (`agents.ts` `verify`); ending a connection goes through `agents.end` only. The person approves on `/connect/approve/:uid` (SPA page; its API sits under the same path for the interaction cookie, behind `requireUser` and an Origin check). `provider.test.ts` covers the configuration (PKCE, rotation, reuse, 90 days, device flow); `e2e/06-connect.spec.ts` covers the flows end to end.
- **Browser sessions end on three clocks** (`apps/server/src/services/session-policy.ts`, Settings → Sign-in security): idle (real input the page reports to `POST /api/session/activity`), maximum length from sign-in (`auth_session.authenticated_at`) and lifetime (any request). Better Auth keeps every session a day longer than the longest maximum length and never refreshes it, so the clocks decide (sessions from before 0009 keep their earlier seven-day cookie); never turn its refresh back on or make polling count as activity. `requireUser` and the guard in front of Better Auth (`http/auth-guard.ts`) check the clocks with the row locked; an ended session keeps its row and reason (`session_ended`) until the hourly cleanup. A session Better Auth creates to replace a live one inherits its clocks through the after hook in `auth/auth.ts`. `app/session-guard.tsx` warns on the page; `e2e/12-session.spec.ts` moves the clocks in the database (`E2E_DATABASE_URL`) and must stay last.
- **Two designs, one app.** Settings → General → Design (`general.design`, `regular` by default) chooses the look for the whole installation: **Regular** (the Spectrum look of #29: the page as one floating card on a grey canvas, a large page title with its icon, Inter, white cards with a ring and a soft shadow, roomy rows without status edges, icons in figures, pills and dialog headers, figures that count up) or **Compact** (the v3 design language: Onest, tinted flat panels, denser). They differ in look only; functions, texts and behaviour are the same. The server keeps the choice in memory (`ctx.settings.design()`, loaded after migrations and updated where General is stored; this assumes one server process) and writes it on `<html data-design>` of every page in `src/http/web.ts`. In the app, `src/lib/design.ts` alone reads or sets the attribute, `src/app/design-sync.tsx` applies a saved choice at once (no reload), the token values in `index.css` differ per design, `regular:` and `compact:` variants may change classes, and only the presentational components in `src/components/skin/` may draw differently; `design.test.ts` enforces this. Where the designs place a control differently (the sidebar fold, the workers status), both copies exist and each design hides the other with `display: none`, so the keyboard order follows what is seen; the shell grid draws Regular's page card behind the bar and the page, so the document order is the same in both. `e2e/07-design.spec.ts` checks the layout of each design, not just its colours. A new feature is built once; give it both looks through tokens and variants. `scripts/verify.sh` runs the one end-to-end suite once per design, each on a fresh stack (`E2E_DESIGN`), and both must pass; `--design` runs one of them, as each CI job `E2E (<design>)` does.
- `apps/worker`: outbound-only agent for an n8n Docker host. The only component with the Docker socket. Never gets database credentials.
- `packages/skill`: the agent skill (`n8n-ops/SKILL.md` and `scripts/`), served by the server at `/connect/skill/` with the public URL filled in (`oauth/skill.ts`, `SKILL_DIR`). Its command exists three times with one contract: `n8n-ops.mjs` (Node 20+, the reference), `n8n-ops.ps1` (Windows PowerShell 5.1 and PowerShell 7) and `n8n-ops.sh` (POSIX sh and curl); `scripts/n8n-ops` picks one. A change to one changes all three: same commands, JSON output, error codes, connection file format and lock protocol. The connection belongs to the computer user (`~/.n8n-ops`, shared by every install of the skill), never to the skill's folder, which the command never writes: tools that install skills from Git link or copy `packages/skill/n8n-ops` as it is, without the address filled in, and the command keeps the address once connected. `test/contract.test.mjs` runs the same suite against each version (Linux in Checks, Windows and macOS in their CI jobs); `oauth/skill.test.ts` runs them against the real authorization server.
- `packages/shared`: schemas, the API key capability table and the tar format, shared by server, worker and UI. `@n8n-ops/shared/archive` (age + gzip) is Node only; never import it from the UI. Imported as TypeScript source; no build step.
- `config/tsconfig.base.json`: shared compiler settings. `biome.json` stays at the root (see traps).
- `docker/`: Dockerfiles with per-Dockerfile ignore files, the toolchain image, the development Compose template, `verify-queue.yml`, and `env/*.env.example`, from which the scripts make each stack's env files.

## Commands

All scripts are Bash for WSL or Linux with Docker. Node, pnpm, shellcheck and shfmt run inside the toolchain container, so the host needs only Docker.

- `scripts/local.sh build|up|start|down|status|logs|nuke`: development stack.
- `scripts/verify.sh [--changed [BASE]] [--guards-only] [--skip-guards] [--skip-integration] [--design regular|compact] [--only checks|integration|e2e]`: the only verification entry point. CI runs the same script, one job per part (`--only`): Checks, Integration, and the end-to-end tests once per design. Without `--only` it runs every part.
- `scripts/try-pr.sh <number>|status|restore`: run a pull request on the development stack.
- Releases: the **Release** workflow (Actions → Release → Run workflow on `main`, choose patch, minor or major) reuses the CI run of the commit on `main` when the newest one succeeded (waiting up to 30 minutes for one that still runs) and runs the whole CI on the commit otherwise (`scripts/ci-result.sh` decides, and checks a reused run again right before publishing), then `scripts/release.sh`: release commit and tag, both images on GHCR (the version, then `:latest`) and the GitHub Release from the CHANGELOG section. A run that stopped halfway is finished by the next run (a new Run workflow, not "Re-run failed jobs"). `scripts/test-release.sh` (run by the guards) covers each way a run can stop, `scripts/test-ci-result.sh` which CI run counts. Never deploys.
- Ad-hoc commands in the toolchain: `source scripts/lib/common.sh && build_toolchain && in_toolchain "pnpm ..."`.

Verify in proportion to the risk of the change, and report what ran and its result:

- **Documentation only** (`docs/`, `README.md`, `AGENTS.md`, `CHANGELOG.md`; nothing under `packages/skill`, whose `SKILL.md` is served to agents): `scripts/verify.sh --changed`, which then runs only the guards.
- **Small and low risk**: a contained change in `apps/server` or `packages/shared` that touches none of security or permissions, encryption, deleting, restoring or retaining data, the contract between server, worker, UI and skill, migrations, dependencies, or build and Compose configuration. For a bug fix, its regression test must be a unit test, run locally to show that it fails without the fix and passes with it. Run `scripts/verify.sh --changed --skip-integration` and open the pull request; CI runs the integration and end-to-end tests. The change is done only when every check is green.
- **Anything else**, including a bug fix whose regression test is an integration test and every change to `apps/web`, `apps/worker`, `packages/skill`, `docker/`, `scripts/`, `.github/` or the root configuration: the full `scripts/verify.sh` before opening the pull request.

On a pull request, CI runs the guards, the unit tests of the changed packages and their dependents, and the integration and end-to-end tests in full, in parallel jobs (the end-to-end tests one job per design). When only Markdown files, `docs/` or `LICENSE` changed, it runs only the guards.

## Traps

- A development stack made before it generated its own secrets (its `docker-compose-dev.yml` names `docker/dev.env`) does not start until `scripts/local.sh migrate` has run once: it points the copy at the generated files (keeping a backup, `docker-compose-dev.yml.before-secrets`), makes them, and moves the kept database to its new password; a run that stops resumes. When the env directory is lost while the database is kept, the scripts stop instead of making new secrets that would not open it.

- pnpm 12 blocks dependency install scripts. Allow a package explicitly under `allowBuilds` in `pnpm-workspace.yaml` only when it needs one.
- Biome 2 must find `biome.json` at the repository root; a config under `config/` fails with "nested root configuration".
- Development and verification data must live on the Linux file system, not under `/mnt/c`; PostgreSQL fails on the Windows mount.
- `apps/web/src/lib/utils.ts` re-exports `cn` from the `cn` package. That is how the current shadcn preset works; do not "fix" the import.
- Vitest in `apps/web` only includes `src/**/*.test.ts(x)`; the Playwright specs in `e2e` run through `scripts/verify.sh` against the container stack, once per design.
- The repository uses the GitHub noreply address as the local `user.email`; GitHub rejects pushes that expose the private address.
- Sign-in is rate limited (5 per 5 minutes). End-to-end spec files sign in through `signIn()`, which reuses the previous file's session; a new spec that signs in with a password on its own will hit the limit.
- In the verification stack the server sends Telegram calls to a stand-in Bot API inside the Playwright runner (`TELEGRAM_API_URL=http://e2e-runner:8099`) and email to Mailpit (`mail:1025`, API on `mail:8025`). Never point `TELEGRAM_API_URL` anywhere in production.

## Docker

- `docker-compose.yml` (tracked) is the production deployment and references published images on GHCR: `server` and `postgres`, behind Traefik on the external `traefik` network with no published port, data in `./data` and `./postgres-data`. A worker runs on an n8n host from the compose file that Workers → Add worker generates (`apps/server/src/lib/worker-install.ts`), not from this file.
- `docker-compose-dev.yml` (root, ignored, never committed) is the development stack. Create it with `cp docker/docker-compose-dev.example.yml docker-compose-dev.yml` and use it only through `scripts/local.sh`. CI, verify and release use the tracked template instead.
- Compose files never contain `build:`; the scripts build images explicitly. The guard in `scripts/verify.sh` enforces it.
- Runtime variables come from an `env_file`: `.env` in production (contract in `.env.example`); for development and verification, one generated file per service in the stack's env directory (`N8N_OPS_ENV_DIR`: `<data dir>/env` for development, a temporary directory per run for `scripts/verify.sh`), made by `write_stack_env` from `docker/env/*.env.example` with new random secrets, owner-only (0700 and 0600), never rewritten. The worker's file has no database credentials. The production `postgres` gets only its three `POSTGRES_*` values through `environment`, so the server's secrets never reach it. Compose interpolation is limited to `VERSION`, `DOMAIN` and the `POSTGRES_*` credentials in production, and to image tags, the host port, the data directory, the Docker socket group and `TELEGRAM_API_URL` (empty except under `scripts/verify.sh`) in the development template, where the scripts set them.
- Every application container runs as a non-root user and has a real health check. Data-directory ownership is fixed inside the image, never by a helper container or a manual `chown`: the `server` and `worker` images start as root only to hand `/data` to `node` (`docker/server-entrypoint.sh`, `docker/worker-entrypoint.sh`; the server's also hands over the top folder of `/backups` when a host folder is mapped there), then run as `node` with no capability left; their health checks drop to `node` too (`docker/as-node.sh`), and commands run in them with `docker compose exec -u node`. Without the socket proxy, the worker image also gives `node` the Docker socket's group, read from the socket, so nothing is filled in by hand. `scripts/local.sh status` and `scripts/verify.sh` fail if a process of `server`, `postgres` or `worker` runs as UID 0. `socket-proxy` (wollomatic/socket-proxy, allowlist of ping, listing containers to find n8n queue workers (never inspecting one), and exec in the listed n8n containers) is the one container that runs as root, only to open the socket that root owns: `check_socket_proxy` requires all capabilities dropped, no new privileges, a read-only file system and no published port. The development and verification stacks use the same layout the Add worker dialog generates. The dialog gives one `docker-compose.yml` with the server URL and the pairing token in it: no commands, no `.env`.
- Persistent data uses bind-mounted host directories, not named volumes. `down` keeps them; only a confirmed `nuke` deletes the validated development data directory.
- Logs go to stdout and stderr.

## Safety

- Never change a production n8n instance (environment flags, restarts, API key creation) without explicit approval from the owner.
- Development and tests use disposable containers, never production instances.
